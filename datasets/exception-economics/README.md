# Exception Economics dataset v1.0.0

Two thousand synthetic back-office work items with known answers, a labour model, and
a scorer that turns the two into the four figures a chief financial officer actually
needs: automation rate, what the wrong automations cost in rework minutes, reviewer
minutes per thousand items, and net cost per item at a stated confidence threshold.

The point of the suite, in one sentence from the charter: a system that automates
everything and is wrong on a tenth of it can be more expensive than one that automates
half and is right.

The data is synthetic. Every company, person, address and identifier was generated by
`generate.py`. Read `datasheet.md` before quoting a number from it.

---

## It runs with no model API, and here is why that is honest

This suite scores **a decision policy over labelled items**. For every item the policy
either completes it without a person or routes it to one, and where it completes an
item it is either right or wrong. Automation rate, wrong-automation rework, reviewer
minutes and net cost all follow from those two facts plus the labour model. All of it
is arithmetic over ground truth, so it runs in an environment with no interface keys
and no network.

That is also the limit of what the numbers mean. They describe a policy and a
threshold. They describe no vendor's system, and every table this suite produces says
so on its face.

The dataset ships a **reference decision policy**: a synthetic confidence and proposed
outcome generated with each item, shaped by the item's tier. It is a property of the
dataset. It is not a measurement of any model. It exists so that the arithmetic can be
demonstrated, checked and reproduced before any system exists to score.

### Dropping in a real system

Write one JSON object per line, one line per item:

```json
{"item_id": "EE-0001", "proposed_outcome": "recon:matched:PO-446576", "confidence": 0.91}
```

`proposed_outcome` uses the encoding in `outcomes.py`:

| Work type | Encoding | Example |
|---|---|---|
| `ticket_triage` | `route:<category>/<priority>[/escalate]` | `route:billing_dispute/p2/escalate` |
| `kyc_case` | `kyc:<decision>[/<reason_code>]` | `kyc:refer/name_mismatch` |
| `invoice_po_recon` | `recon:<decision>:<po>\|<po>` | `recon:matched:PO-446576` |

Three optional booleans, all defaulting to false: `processing_failure`,
`validation_failure`, `policy_flag`. Then:

```bash
python3 score.py --predictions runs/vendor-a.jsonl --label "Vendor A" \
    --out ../../results/exception-economics-v1.0/scores-vendor-a.json
```

An item with no line in the predictions file is scored as a processing failure and
counted as one. It is never dropped from the denominator, per charter 3.1.2.

## Regenerate everything from a seed

Five commands, all of them under a second on one core.

```bash
pip install pyyaml --break-system-packages

python3 generate.py --seed 20260902   # 2,000 items, ground truth, manifest, sample
python3 validate.py                   # 24,000-odd checks; exits non-zero on any failure
python3 score.py  --out ../../results/exception-economics-v1.0/scores-baseline.json
python3 drift.py  --out ../../results/exception-economics-v1.0/drift.json
python3 report.py --results ../../results/exception-economics-v1.0
```

`report.py` rewrites every markdown file in the results folder from the two JSON
files, so no figure in a report is typed by hand and no report can drift away from the
numbers it describes.

Deterministic: the same seed produces byte-identical output, and `validate.py` proves
it by regenerating and comparing the hash.

## What is in the set

| Work type | Items | The decision | Ground truth |
|---|---|---|---|
| `ticket_triage` | 790 | Category, priority, and whether the ticket must be escalated | One correct route |
| `kyc_case` | 495 | Pass, refer or reject, with a reason code | One correct decision and reason |
| `invoice_po_recon` | 715 | Match the invoice to one or more purchase orders, or hold it | One correct decision and purchase-order set |

Two populations inside those 2,000 items.

| Population | Items | What it is |
|---|---|---|
| `baseline` | 1,700 | The acceptance set. The frozen labelled set the day-0 measurement is taken on |
| `shifted` | 300 | Tier 5 only. Categories, vendor formats and document sources absent from the baseline, used to build the day-N live samples in the drift simulation |

Charter 4.4.2 makes tier 5 the only tier in which the ninety-day drift simulation is
applied, which is why every shifted item is tier 5.

### Difficulty tiers

Assigned at generation from the parameters in charter 4.4, and recorded on every item
so a reader can verify the tier from the item rather than trusting the label.

| Tier | Items | Sources | Key | Cardinality | Tolerance rules | Ground truth |
|---|---|---|---|---|---|---|
| T1 | 340 | 1 | Exact on both sides | One to one | None | Single answer, no judgement |
| T2 | 425 | 2 | Exact, formatted differently | One to one | One | Single answer |
| T3 | 425 | 2 to 3 | None; name, amount and date window | One to many | Two, interacting | Single answer via a labelling-guide rule |
| T4 | 340 | 3 to 4 | None | Many to many | Three, order dependent | Single answer; the cost of being wrong exceeds review |
| T5 | 470 | 3 to 5 | None | Many to many | Four, order dependent | Two sources disagree; a policy document decides |

`validate.py` checks every one of those six parameters against every item's recorded
tier, so a mislabelled tier fails the build rather than reaching a table.

### Lifecycle and exclusions

Charter 3.1.2: nothing is silently dropped, and every exclusion is counted beside the
figure it was excluded from.

| Lifecycle | Items | Treatment |
|---|---|---|
| `admitted` | 1,892 | In the denominator of every rate |
| `pre_processing_rejected` | 57 | Excluded, counted, rule named on the item |
| `upstream_failure` | 26 | Excluded, counted |
| `in_flight` | 25 | Excluded, counted, open at window close |

### Splits

| Split | Items | Published |
|---|---|---|
| `public_sample` | 100 | Yes, in `sample/`, committed in parts — see `sample/README.md` |
| `private_holdout` | 300 | No. Never |
| `open` | 1,600 | Regenerable from the seed |

Both splits are stratified across work type and tier and drawn from a named stream, so
the assignment is part of the ground truth rather than a property of which folder
exists on disk.

## The labour model

`labour-model.yaml` holds the minutes and the money. Two rules govern it, and
`validate.py` enforces both.

**Every money figure is a placeholder**, marked `placeholder — replace`. The INR and
USD reviewer rates are two independent placeholders: no exchange rate is applied
between them anywhere in the scorer and none should be inferred. Machine cost per item
is zero, because no system has been run and no measured cost per item exists, so every
net cost figure this suite produces is labour only.

**Every minute figure is a modelling assumption** and states its basis in the file.
Not one was measured by a time study, ours or anyone else's. `validate.py` fails the
build if a minute figure appears without a basis, or if it does not say plainly that
it is a modelling assumption.

Three of the eleven error classes carry no minutes at all. A support ticket that needed
escalation and was closed as routine, a know-your-customer case wrongly passed, and an
invoice exception wrongly posted have no detection route inside a monthly measurement
window. Charter 3.15.3 requires those to be reported as an open exposure count with
the class named, never given an estimated minute figure. Inventing a detection time for
an error nobody would find is the exact failure this benchmark exists to expose.

## The ninety-day drift simulation

`drift.py` shifts the input distribution in seven documented steps across ninety days
and re-scores at each one. The steps live in `manifest.json`, not in the scorer, per
charter 3.17.4. Three drivers at the item level, one at the mix level:

| Driver | Level | What changes |
|---|---|---|
| `new_vendor_format` | Item | Vendors move to consolidated statements, milestone billing and marketplace settlements |
| `new_ticket_category` | Item | A product launch introduces ticket categories with no labelled example in the baseline |
| `new_kyc_source` | Item | New identity and residence sources appear in KYC files |
| Seasonal mix | Sample | The work-type weights of the live sample move across the ninety days |

Charter 3.17.1 requires two figures. Frozen-set drift is zero at every step of this
simulation by construction, because the simulation changes the input and nothing else.
That zero is a property of the simulation and not a finding about any system's
stability. Live-distribution drift is the figure the simulation actually produces.

It is a simulation everywhere it appears, in the table, the chart and the prose.

## Files

| File | What it is |
|---|---|
| `generate.py` | The seeded generator. 2,000 items, ground truth, tiers, manifest, public sample |
| `outcomes.py` | Outcome encoding and error classification, shared by the generator and the scorer so they cannot disagree |
| `labour-model.yaml` | Reviewer minutes, rework minutes, reviewer cost. Every money figure a placeholder, every minute a stated assumption |
| `score.py` | The scorer. Three thresholds, a sweep, the minimising threshold, all breakdowns |
| `drift.py` | The ninety-day drift simulation |
| `report.py` | Renders every markdown file in the results folder from the scorer's JSON |
| `validate.py` | Every check that has to pass before a number leaves this folder |
| `ground-truth.jsonl` | The 2,000 items. Rebuilt from the seed rather than committed; hash in the repository's `REGENERATED.md` |
| `manifest.json` | Counts, mixes, drift steps, reference-policy parameters, ground-truth hash |
| `sample/ground-truth.part-*.jsonl` | The 100-item public sample. `cat` the parts to rebuild the file; `sample/README.md` gives the hash |
| `datasheet.md` | Datasheets for Datasets, following Gebru et al. |
| `MANIFEST.md` | Splits, drift steps and the reasoning behind both |
